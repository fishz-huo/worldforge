# 时间轴联动与因果连线 —— 边界情况与验收清单（附录）
> 主稿见 `docs/时间轴联动与因果连线-PRD.md`。本文只讲两件事：**会坏在哪里**、**怎么算做完**。

---
## 9 边界情况
### 9.1 事件没有绑定卡片时，连线怎么办（**本方案最重要的边界**）
连线要落到 `relations` 表，而 `relations` 的两端是**卡片**（`from_id` / `to_id`）。整个仓库里没有任何「条目↔条目」的连线存储，也没有给 `timeline_entries` 留 JSON 列（表结构见 `schema-extra.ts`：只有 `note / state / value / map_id`）。所以规则定死：
1. **两端都绑了卡片**：正常连线，落一条 `relations` 行；
2. **起点没绑卡**：选中它时**不显示**四个拖拽圆点，改为在块右下角显示一个灰色的 `未绑定卡片` 小徽标；鼠标移上去提示 `绑定卡片后才能拉因果线（这条线要存进卡片关系）`；
3. **落点上没绑卡**：橡皮筋拖到它上面**不高亮**、松手不给菜单，松手后顶部提示行显示 `目标事件没有绑定卡片，无法建立连线`（不弹窗、不打断）；
4. **想绑**：在同一个提示条上给一个 `立即关联卡片…` 按钮 → 打开既有 `CardPicker`（复用 `Editor` 里那套），选完卡片后**不自动补连线**，用户重新拉一次（避免"我随手绑了个卡，结果线也自己连上了"这种意外写库）；
5. 已经是「未绑定」状态的既有条目：画布上照常显示，只是不参与连线；冲突检测**照样能检出**它（冲突只看 `track_id` 与刻度，不看卡片）。

### 9.2 同一条 relations 在时间轴上重复连线
三种"重复"要分开处理，不能一律去重：
| 情况 | 例子 | 处理 |
| --- | --- | --- |
| **同一条关系被两端各画一次** | `焚天陨落 → 灵息战争` 一条关系，画布上出现两条反向箭头 | 去重：边的键 = 卡片对（无序）`[min(from,to), max(from,to)]`，**一条关系只画一条线**，箭头方向仍由 `from → to` 决定 |
| 两个不同条目映射到同一张卡 | 「焚天陨落」和「焚天余烬」都绑定了卡片 A | 画布上**合并成一条线**（自卡片 A 到卡片 B），但线中点显示一个小数字 `2` 表示有 2 条关系；点中线条时列出这 2 条，可分别删 |
| 用户重复拉了同一条关系（同 label 同方向） | 又选了一次「导致」 | `useEdgeDrag` 在松手前先查重：已存在 `from/to/label` 完全相同的行 → **不再新增**，提示 `这条连线已存在`，并让用户决定是否改关系类型（改类型 = `updateRelation`，不是新增） |
> 去重的实现落点：一个 `useMemo` 建 `Map<edgeKey, Relation[]>`，画布与右栏「因果关系」区**共用同一份**，避免两处算法不一致（这是时间轴最容易"两处各算一遍"的地方）。

### 9.3 冲突检测的性能：1000 条条目下怎么不卡
| 手段 | 做法 |
| --- | --- |
| **只在数据变化时算** | `useTimelineConflicts` 的依赖只有 `entries / tracks / cards / ignoredConflicts`。**特别地：游标移动不重算**（`cursor` 只影响高亮，不影响冲突）——这一点必须写进注释，否则很容易顺手把 cursor 加进依赖 |
| 规则一别做 O(n²) | 按 `track_id` 分桶后，桶内按 `start_t` 排序；只用 `overlaps()`（`src/types/timeline.ts` 已有）比较「当前条目 vs 之后那些 `start_t <= 当前 end_t` 的条目」，排序后可以提前 break。1000 条均匀分布时比较次数是数千次量级，不是一百万 |
| 规则二走索引 | 先建 `Map<track_id, 角色卡>`（每泳道取第一条有 `card_id` 的条目，与 `TimelineLaneLabel` / `MomentPanel` 同一口径），再对每个条目查一次 `death_t`，O(n) |
| 结果缓存 | 检出结果按条目 id 索引成 `Map<entryId, Conflict[]>`，画布上的红三角是 O(1) 查表；列表直接读同一份 |
| 单条条目冲突数封顶 | 一个条目最多列 3 条冲突（多了右栏没意义），其余折叠成 `等 N 条` |

**性能预算（实现后必须实测填表，不许写「应该流畅」）**
| 指标 | 目标 | 测法 |
| --- | --- | --- |
| 1000 条条目首次检出耗时 | < 30ms | `console.time` 包住检出函数（dev） |
| 拖动条目（`start_t` 每帧变）时的重算 | 每帧 < 8ms | Performance 面板看长任务 |
| 200 条连线同时渲染 | 无掉帧 | 造 200 条 relations 后拖动滚动条 |
| 拖动游标 | 冲突**不重算**（验证手段：在检出函数里打计数日志，拖一次游标数字不许涨） | dev 日志 |

### 9.4 其它边界
| 情况 | 处理 |
| --- | --- |
| 条目区间非法（`end_t < start_t`） | 已有行为是表单里红字提示；冲突检测里先 `Math.min/max` 归一化再比较，不许因此漏检或误检 |
| 瞬时事件（`instant=1` / `end_t=null`）的重叠 | 用既有的 `entrySpan(entry, minSpan)` 口径给一个最小宽度参与重叠判定——**与画布上看到的宽度一致**，否则会出现"看着重叠、没报冲突" |
| 角色卡没填 `death_t` | 视为在世，规则二对它**永不出警** |
| 角色卡没填 `birth_t` | 与规则二无关（这条只用到 `death_t`）；`TimelineLaneLabel` 显示的"未填出生刻度"保持现状 |
| 角色泳道绑的卡片不是角色类型 | 只按 `fields.death_t` 是否存在判断，不看卡片 type（`death_t` 是角色卡的字段，见 `card-types.ts`；取不到就是没有） |
| 条目被删除 / 换了泳道 | 检出结果随 `entries` 变化自动更新；忽略名单里那些"签名不再对应任何现存条目"的项直接忽略不计 |
| 连线指向已删除的卡片 | 关系行还在时，边照样画但变灰虚线 + 断开标记，点击提示 `目标卡片已删除`，可在右栏删掉这条关系（复用 `RelationEditor` 的 `（已删除的卡片）` 文案口径） |
| 一条关系被 `RelationEditor` 那边改了 label | 时间轴上线的样式**立刻跟着变**（样式只由 `label` 决定，没有第二处状态副本） |
| 泳道被隐藏（`track.hidden=1`） | 该泳道的条目本来就渲染为空数组；连到它的边**一并隐藏**（否则会出现"线连到空气里"） |
| 顶栏 `[显示连线]` 关掉后再打开 | 开关状态是视图态，重开模块会回到默认（开）；不落盘 |
| 冲突红三角与选中的环形描边重叠 | 三角放在块**右上角外侧 2px**、`z-20`；选中环用 `ring`（在块边界上），两者不互斥 |

### 9.5 关于「忽略」要不要落盘（需要你拍板的小决策）
| 方案 | 行为 | 代价 |
| --- | --- | --- |
| **A（本稿默认）** | 忽略只记在**本次会话**内存里；重载后冲突又出现 | 零改动、零风险；缺点是"我上周就确认过了"每次都要再点一遍 |
| B | 忽略名单写进 `worlds.meta.timelineIgnoredConflicts`（`meta` 是现成的 JSON 文本列），随世界观走 | 多一处数据语义；**不需要**动 schema 版本（`WorldMeta` 已有 `[key: string]: unknown`），但会写进备份与快照 |
| C | 给 `timeline_entries` 加一列 / 新建 `ignored_conflicts` 表 | 需要提 `SCHEMA_VERSION` 并写迁移，风险最大 |
> 建议：先做 A，等真的觉得烦了再升 B。C 不建议。

### 10.4 明确"不动的部分"（免得验收时被问）
1. **导出链路零改动**：连线不会出现在 md / word / pdf / txt 导出里（本次不做，若需要另立需求）；
2. 卡片模块的 `RelationEditor` 行为不变（时间轴只是复用同一张表）；
3. 地图模块除顶栏那枚只读探针标签外**零改动**（不动 `maps.period`、不切地图、不写库）；
4. 游标快照（`MomentPanel`）的既有判定不改逻辑，只在它下方追加冲突区块。

## 11 实现顺序建议（每步都能单独验收）
1. **基础联动**（高亮规则函数 + 三态样式 + 游标高亮）：验收 A1 / A2 / A3 / C1 / C2。
2. **冲突检测**（`useTimelineConflicts` + 红三角 + `ConflictPanel`）：验收 A12 / A13 / A14 / A15 / B1 / B2 / B4。
3. **因果连线数据与渲染**（`edgeStyle` + `TimelineEdgeLayer`，先只画已有关系、不可拖）：验收 A7 / A8 / A9 / A10 / B3。
4. **因果连线交互**（`useEdgeDrag` + 圆点 + 四选一菜单 + 删线 + `EntryEditor` 因果关系区）：验收 A6 / A11。
5. **游标探针同步**（store 非落盘键 + 地图顶栏标签）：验收 A4。
6. **移动端微调**（圆点放大、开关收进下拉）：`max-md` 下过一遍 A6。
> 每一步做完各自跑 `npm test` + `typecheck` + 目测对齐，不要攒到最后。第 1 步就要顺手把 `TimelineCanvas.tsx` 的底部提示抽出去腾行数。

## 12 引用与依据（本稿不是凭空设计的）
| 结论 | 依据 |
| --- | --- |
| 连线两端必须是卡片、没有条目级连线存储 | `schema-core.ts` 的 `relations`（`from_id`/`to_id` 为卡片）+ `schema-extra.ts` 的 `timeline_entries` 无 JSON 列 |
| 关系类型只有 `label` 一个自由字段 | `src/types/tag.ts` 的 `Relation` 定义与 `RELATION_SUGGESTIONS` |
| 写入接口已存在 | `cardSlice.ts` 的 `addRelation/updateRelation/deleteRelation`（签名 `{from_id,to_id,label,note?}`） |
| 坐标、行高、游标必须是同一套 | `TimelineCanvas.tsx` 头注释 + `LABEL_COL` / `plotPx` / `toLaneX` 的既有纪律 |
| 冲突判定可直接复用 | `src/types/timeline.ts` 已有 `overlaps` / `entrySpan` / `ageAt` |
| 死亡刻度取值口径 | `MomentPanel.tsx`（`card.fields.death_t` + `cursor > death` → 「已故」）与 `card-types.ts`（`birth_t` / `death_t` 字段定义） |
| 名称列宽度两档 | `useTimelineView.ts` 的 `LABEL_COL=144` / `LABEL_COL_NARROW=80`（窄屏 80px） |
| 侧栏/检查器已可收起 | `TimelineModule.tsx`（时间轴为横向信息，故改为工具条 + 抽屉） |
| 游标被反复报告"没对齐" | 时间轴历史教训（同一坐标系写了两遍 → 刻度/条目/游标各差一点） |
| 不引入依赖、文件 ≤200 行 | 需求文档 P5 / R-10 与 `docs/架构设计.md` §4 |
